# Концепция языка

## 1. Общая идея

Язык задуман как низкоуровневый компилируемый язык с ручным контролем там, где он действительно нужен, но с максимально автоматизированным анализом памяти и зависимостей в обычном коде.

Основные цели:

* близкая к нативной производительность;
* предсказуемое поведение;
* отсутствие необходимости в тяжёлом runtime/GC;
* автоматический статический анализ жизненного цикла данных;
* возможность полностью ручного управления памятью;
* максимально простая модель изменения состояния;
* явность важных действий в исходном коде;
* безопасность памяти без необходимости воспроизводить модель Rust один в один.

Компилятор должен по возможности выводить необходимые действия из программы на этапе компиляции и генерировать обычный низкоуровневый код.

---

# 2. Неизменяемость по умолчанию

Все значения и состояния по умолчанию считаются неизменяемыми.

Изменение существующего состояния требует явного `mut`.

Пример:

```text
x = 10
mut x = 15
mut x += 5
```

Концептуально это:

```text
x₀ = 10
  ↓ mut
x₁ = 15
  ↓ mut
x₂ = 20
```

`mut` не является постоянным свойством переменной.

Это не аналог:

```text
mutable x
```

и не разрешение:

> «эту переменную теперь можно менять».

Смысл `mut`:

> «я прямо сейчас выполняю изменение состояния».

После изменения новое состояние снова считается неизменяемым.

Основной принцип:

> Не объявлять разрешение на изменение, а явно обозначать само изменение.

---

# 3. Состояния данных

Изменение объекта/значения рассматривается как переход между состояниями.

Например:

```text
x = 10

mut x = 20
```

означает переход:

```text
state₀ → state₁
```

где:

```text
state₀: x = 10
state₁: x = 20
```

Это важно для модели ссылок.

---

# 4. Обычное `=` — ссылка на текущее состояние

Обычное присваивание не обязательно означает копирование данных.

Например:

```text
a = 20
b = a
c = b
```

может означать:

```text
a ─┐
b ─┼──→ [20]
c ─┘
```

Все три имени связаны с одним текущим состоянием данных.

При этом связь `b = a` является контрактом с конкретным состоянием.

Если затем происходит:

```text
mut a = 30
```

то создаётся новое состояние `a`.

Старый контракт:

```text
b = a₀
```

больше не существует.

`b` не превращается в dangling reference. Старая версия состояния просто перестаёт быть допустимой для дальнейшего использования через этот контракт.

Чтобы снова получить `b`, необходимо явно написать:

```text
b = a
```

После этого:

```text
b → a₁
```

---

# 5. Контракт состояния

Запись:

```text
b = a
```

можно рассматривать как:

> `b` имеет право обращаться к текущему состоянию `a`.

После:

```text
mut a = ...
```

это состояние изменяется, поэтому контракт с предыдущим состоянием сгорает.

Таким образом, обычная ссылка намеренно является относительно хрупкой.

Это позволяет упростить правила безопасности: изменение состояния явно разрывает старые зависимости, которые были привязаны к предыдущему состоянию.

---

# 6. Явная долговременная ссылка

Предполагается отдельный синтаксис для ссылки, которая должна быть привязана не к конкретной версии состояния, а к самой памяти/объекту.

Предлагаемый вариант:

```text
#=
```

Например:

```text
a = 20
b #= a

mut a = 30
```

В этом случае:

```text
b
```

остаётся связанной с той же памятью/объектом и после изменения `a` может видеть новое значение.

Разница:

```text
b = a
```

— ссылка на конкретное состояние.

```text
b #= a
```

— явная привязка к самому объекту/памяти.

`#=` не должен делать ссылку бессмертной: если сама память/объект уничтожена, такая ссылка тоже становится недействительной.

Главная идея:

> Обычная ссылка короткоживущая и привязана к состоянию. Долгоживущая ссылка должна быть выражена отдельным синтаксисом.

---

# 7. Ссылки на элементы

Ссылка может быть создана непосредственно на нужный элемент.

Например:

```text
b = a[0]
```

означает ссылку на соответствующий элемент текущего состояния.

Если `a` затем изменяется:

```text
mut a = ...
```

обычная связь с предыдущим состоянием `a[0]` прекращается.

Даже если после изменения в `a[0]` случайно находится такое же значение, это уже новое состояние.

Если необходимо сохранить привязку к самой памяти/объекту, используется специальная долговременная форма ссылки.

---

# 8. `mut` и безопасность

Компилятор получает очень важную информацию непосредственно из синтаксиса:

```text
mut
```

означает конкретную точку перехода состояния.

Поэтому компилятору не нужно угадывать намерение программиста.

Он может анализировать:

* какие ссылки существуют;
* к каким состояниям они привязаны;
* где состояние изменяется;
* какие зависимости после этого становятся недействительными;
* где значение ещё используется;
* где оно больше недостижимо.

Если явное изменение нарушает какое-либо правило языка, компилятор указывает на соответствующую точку изменения.

---

# 9. Автоматическое управление памятью

Ручное управление памятью не удаляется из языка.

Остаются два режима.

### Автоматический

По умолчанию компилятор анализирует программу и самостоятельно определяет:

* где необходима память;
* где объект создаётся;
* где данные перестают быть нужны;
* где память можно безопасно освободить.

При этом не требуется тяжёлый runtime или garbage collector.

Компилятор может вставлять необходимые операции непосредственно в сгенерированный машинный код.

### Ручной

Программист при необходимости может явно управлять памятью.

Например, концептуально:

```text
p = alloc(...)
...
free(p)
```

Если компилятор видит явное ручное управление, он понимает, что соответствующий участок контролируется программистом, и не должен параллельно пытаться автоматически освобождать ту же память.

Таким образом:

> автоматическое управление является режимом по умолчанию, а ручное управление остаётся доступным там, где требуется полный контроль.

---

# 10. Автоматический анализ жизненного цикла

Компилятор может строить граф управления и зависимостей программы.

Например:

```text
x = random_number

if x == target:
    storage.add(x)
else if x < target:
    discard(x)
else:
    send_external(x)
```

Все варианты поведения присутствуют в исходном коде.

Компилятор анализирует каждый путь:

```text
             x
             |
       +-----+-----+
       |     |     |
     store discard send
       |     |     |
      alive dead external
```

Если значение передано в хранилище, его жизненный цикл продолжается через это хранилище.

Если значение явно отброшено и дальнейшего пути использования нет, оно становится мёртвым.

Если значение передано во внешнюю операцию, эта операция должна иметь определённый контракт.

Не существует отдельного состояния:

> «значение куда-то ушло, но неизвестно куда».

Если операция присутствует в программе, у неё есть конкретное назначение или семантический контракт.

---

# 11. Консервативный анализ

Компилятор не обязан уметь доказать абсолютно всё.

Если он не может доказать, что память больше не нужна, безопасный вариант:

> не освобождать её автоматически в этой точке.

То есть:

```text
не доказано, что мёртвое
        ↓
не освобождать
```

а не:

```text
кажется, что мёртвое
        ↓
освободить
```

Таким образом, ограниченность статического анализа не разрушает саму концепцию автоматического управления памятью.

Главное требование:

> автоматическое освобождение должно происходить только там, где компилятор доказал его безопасность.

---

# 12. Условия и ветвления

Ветвления не являются принципиальной проблемой для анализа.

Например:

```text
if condition:
    use(x)
else:
    discard(x)
```

Компилятор знает оба возможных пути.

Он может построить CFG:

```text
       condition
        /      \
      true    false
       |        |
     use(x)  discard(x)
        \      /
          end
```

Задача анализа — определить свойства `x` на всех возможных путях.

---

# 13. Циклы

Циклы могут иметь неизвестное количество итераций:

```text
while condition:
    use(x)
```

Это не означает, что анализ невозможен.

Компилятор может использовать стандартный data-flow/fixpoint-анализ.

Если после определённой точки значение не может быть использовано ни по одному дальнейшему пути, оно считается мёртвым.

Если доказать это невозможно, память сохраняется.

Таким образом, неизвестное количество итераций не требует знания конкретного будущего исполнения программы.

---

# 14. Главное различие: runtime и compile-time

Компилятору не нужно заранее знать:

> «какая именно ветка выполнится».

Ему нужно знать:

> «какие ветки вообще существуют и какие действия возможны на каждой из них».

Runtime выбирает конкретный путь.

Compile-time анализирует множество возможных путей.

Поэтому наличие условий и циклов само по себе не противоречит автоматическому управлению памятью.

---

# 15. Внешние операции

Если данные покидают обычный контекст программы, это должно происходить через явную операцию:

* функция;
* структура;
* файл;
* API;
* устройство;
* системный вызов;
* другая внешняя граница;
* явное отбрасывание.

Для таких операций компилятору нужен контракт.

Например, условный вызов:

```text
send_external(x)
```

должен иметь определённую семантику относительно `x`.

Внешний код не обязан быть полностью проанализирован компилятором, но граница между ним и языком должна быть описана явно.

---

# 16. Вывод об автоматической памяти

Таким образом, автоматическое управление памятью может быть реализовано не как GC, а как **статический анализ + генерация необходимых операций**.

Условная схема:

```text
Source
  ↓
Lexer
  ↓
Parser
  ↓
AST
  ↓
Semantic Analysis
  ↓
State / Reference Analysis
  ↓
Lifetime / Data-flow Analysis
  ↓
Dependency Graph
  ↓
сгенерированные alloc/free
  ↓
собственный IR
  ↓
LLVM IR
  ↓
Machine Code
```

Полученный код может быть обычным нативным кодом без необходимости постоянно иметь работающий сборщик мусора.

---

# 17. Стоимость анализа

Более глубокий анализ может увеличить время компиляции.

Это считается приемлемым компромиссом, если взамен получается:

* предсказуемый runtime;
* отсутствие обязательного GC;
* автоматическое управление памятью;
* безопасность;
* возможность ручного контроля.

То есть предпочтение отдаётся:

> больше работы во время компиляции → меньше работы во время выполнения.

---

# 18. Ручной и автоматический режимы не должны мешать друг другу

Компилятор должен видеть границы ответственности.

Условно:

```text
automatic region
    ↓
compiler manages lifetime
    ↓
manual region
    ↓
programmer manages lifetime
    ↓
automatic region
```

Это позволяет использовать автоматический режим почти везде, но при необходимости спускаться на полностью ручной уровень.

Для низкоуровневого языка это особенно важно, поскольку некоторые программы требуют абсолютного контроля над размещением и временем жизни памяти.

---

# 19. Параллелизм и зависимости

Планируется возможность автоматически выполнять независимые операции параллельно.

Программист описывает операции и их зависимости, а компилятор строит граф.

Например:

```text
A: compute X
B: load files
C: process(X, B)
```

Граф:

```text
A ── X ──→ C
B ───────→ C
```

`A` и `B` могут выполняться независимо.

`C` начинается только после получения необходимых результатов.

Если `B` состоит из независимых операций:

```text
file1 ─┐
file2 ─┼──→ B
file3 ─┘
```

загрузка может выполняться параллельно.

---

# 20. Односторонние зависимости

Зависимость должна существовать только там, где она действительно нужна.

Если:

```text
A → B
```

это не означает, что `B → A`.

Например, если результат `A` нужен `B`, то достаточно:

```text
A
↓
B
```

Независимые части программы не должны искусственно блокировать друг друга.

---

# 21. Автоматическое планирование

Компилятор может преобразовать зависимости в граф задач и затем выбрать способ их выполнения:

* последовательно;
* параллельно;
* на отдельных потоках;
* через worker pool;
* через другой лёгкий scheduler.

Главная идея:

> программист описывает семантические зависимости, а не вручную расставляет каждую точку синхронизации для независимых операций.

При этом низкоуровневые примитивы вроде mutex/atomic/channel при необходимости всё равно могут существовать.

---

# 22. Параллелизм не равен безопасности памяти

Параллельное выполнение рассматривается как отдельный уровень.

Программа может быть:

* memory-safe, но логически неправильной;
* корректной по зависимостям;
* некорректной из-за неправильной организации параллельных операций.

Поэтому безопасность памяти и корректность параллельной логики не обязательно должны быть одной и той же системой правил.

---

# 23. Собственный IR

Предполагается наличие собственного промежуточного представления.

Оно должно отражать особенности самого языка:

* состояния;
* переходы `mut`;
* обычные state-bound ссылки;
* долговременные ссылки `#=`;
* жизненный цикл объектов;
* зависимости;
* операции памяти;
* потенциальный параллелизм.

После анализа собственный IR можно преобразовывать в LLVM IR.

Это позволяет не пытаться заставить LLVM понимать семантику языка напрямую.

---

# 24. LLVM как backend

Для первой реализации предпочтительно использовать Rust.

Причины:

* стабильная экосистема;
* безопасность самого компилятора;
* удобная работа со структурами данных;
* возможность реализовать сложный статический анализ без большого количества ручной работы с памятью;
* LLVM уже предоставляет оптимизацию и генерацию машинного кода.

Сам язык при этом совершенно не обязан копировать модель Rust.

Rust используется как инструмент для написания компилятора, а не как образец семантики разрабатываемого языка.

---

# 25. Почему не обязательно использовать Zig

Zig интересен для низкоуровневых задач, но если инфраструктура и инструменты вокруг языка активно меняются, это создаёт дополнительный риск для долгосрочного проекта.

Если проект будет развиваться долго, изменения самого Zig могут потребовать адаптации компилятора.

Rust + LLVM дают более предсказуемую основу для экспериментов с собственным языком.

---

# 26. Главная философия языка

Вся концепция сводится примерно к следующим принципам:

### 1. Неизменяемость по умолчанию

Данные не меняются без явного действия.

### 2. `mut` обозначает действие

`mut` — это не постоянное разрешение, а конкретный переход состояния.

### 3. Ссылки по умолчанию привязаны к состоянию

```text
b = a
```

создаёт контракт с текущим состоянием.

### 4. Изменение состояния разрывает старые state-bound контракты

После:

```text
mut a = ...
```

старые обычные ссылки на предыдущий state становятся недействительными.

### 5. Долгоживущая ссылка должна быть явной

```text
b #= a
```

выражает привязку к самому объекту/памяти.

### 6. Память по умолчанию анализирует компилятор

Компилятор пытается вывести жизненный цикл и вставить необходимые операции.

### 7. Ручное управление остаётся

Если нужен абсолютный контроль, программист может явно управлять памятью.

### 8. Невозможность доказать смерть не означает невозможность автоматического управления

Компилятор может быть консервативным.

### 9. Независимые действия могут выполняться параллельно

Зависимости образуют граф, который может использоваться для автоматического планирования.

### 10. Язык должен быть явным

Компилятор анализирует семантику, выраженную в программе. Он не должен угадывать намерения программиста там, где это не требуется.

---

# 27. Ключевая формула проекта

> **Максимум анализа во время компиляции, минимум обязательной работы во время выполнения.**

И при этом:

> **Автоматизация по умолчанию, ручной контроль по требованию.**

А модель изменения состояния:

> **Не «я разрешаю изменять это», а «я изменяю это прямо сейчас».**
