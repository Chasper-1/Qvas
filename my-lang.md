Сам язык
Цель — сделать нативный язык без GC, простой примерно как Go, но безопасный по памяти не хуже Rust.
Ты не стремишься напрямую конкурировать с Rust или Zig в их нишах. Основная цель — превзойти Go по сочетанию простоты, безопасности и нативности.
При этом если в итоге язык окажется способен конкурировать с Rust по производительности и возможностям — это хорошо, даже если изначально такой цели не было.
Язык должен подходить для широкого класса нативных задач:
приложения;
веб-софт;
игры;
утилиты;
системное программирование;
embedded/микроконтроллеры.
Для embedded компилятор должен уметь проверять код и делать его достаточно лёгким для микроконтроллеров.
Владение и память
Все данные неизменяемы/доступны для чтения по умолчанию.
Владение существует всегда.
Чтение не забирает владение.
Чтобы изменить значение, нужен ownership и эксклюзивный mutable-доступ.
Пока значение читается другими, владелец не может его изменить.
mut означает именно такой эксклюзивный режим.
Пока значение находится в mut, оно недоступно другим читателям.
После изменения значение возвращается владельцу, и чтение снова разрешается.
Если активный читатель/ссылка не был корректно завершён или возвращён, компиляция должна завершиться ошибкой.
Владение при чтении не исчезает: владелец остаётся владельцем.
Копирование остаётся обычным способом получить независимое значение.
Это должно давать безопасность памяти уровня Rust, но с гораздо более простой моделью.
В структурах данных ownership можно брать на уровне конкретного значения/элемента, не обязательно блокируя всю структуру. Например, можно забрать один элемент вектора, изменить его, вернуть, после чего снова разрешить чтение.
Тебе не нужен Rust-подобный сложный анализ всех возможных aliasing-сценариев, если твоя модель может гарантировать безопасность более прямыми правилами.
Одновременное изменение одного значения из разных потоков ты не считаешь чем-то, ради чего нужно усложнять основную модель; для таких случаев можно использовать синхронизацию или другую организацию данных.
Асинхронность может быть менее тонкой, чем в Rust: в некоторых случаях поток может просто ждать ответа. При необходимости производительную асинхронность всё равно можно написать вручную.
То есть ты сознательно готов пожертвовать некоторой выразительностью в редких случаях ради значительно более простой модели.
Обучение
Одна из главных целей — чтобы базовую модель языка можно было понять примерно за пять минут и сразу применять.
Ты хочешь сделать обучение максимально простым.
Возможно, будут два варианта обучения:
для новичков — с базовыми концепциями;
для опытных — без повторного объяснения очевидных основ.
Знание Rust во втором варианте будет плюсом, но не требованием: человек без Rust просто прочитает больше материала.
Макросы

Твоя концепция макросов — именно шаблон кода.

Макрос получает код/выражения снаружи.
Внутри ему не обязательно знать конкретные типы данных.
После подстановки получается обычный код, который дальше нормально типизируется и оптимизируется.
Макрос не должен быть универсальной заменой функциям.
Если что-то просто принимает значения и возвращает значения — это функция.
Макрос нужен именно там, где работа идёт с кодом как с шаблоном.
Ты предпочитаешь такой подход Zig-подходу с comptime.
Для тебя comptime Zig выглядит скорее как выполнение обычного языка во время компиляции, тогда как твой макрос — буквально шаблон.
Идея — максимально инлайнить/раскрывать такие шаблоны и не создавать лишней runtime-стоимости.
Макросы можно будет использовать для большого количества шаблонного кода.
Алиасы

Ты хочешь сделать алиасы готовых слов языка.

Например, если оригинал использует:

fn

можно сделать алиас и писать:

функция

или вообще:

жопа

если человеку так хочется.

Это именно замена уже существующего слова, а не новая семантическая конструкция.
Алиас превращается в эквивалент оригинального канонического слова.
Можно фактически локализовать синтаксис под свой язык.
При этом канонический синтаксис остаётся единым для экосистемы.
Ты хочешь делать это отдельным уровнем/форматом файла, условно как отдельное расширение.
Алиасный файл преобразуется в обычный валидный файл на оригинальном синтаксисе.
Потом уже обычный файл компилируется.
Обратное преобразование не должно создавать постоянный второй исходник проекта.
В Git/GitHub должен находиться единый канонический синтаксис, чтобы не было двух конкурирующих версий одного файла.
Алиасы — личное представление разработчика: каждый может взять один и тот же канонический код и использовать собственный набор алиасов.
Поэтому твой личный синтаксис не загрязняет общий исходный код проекта.
Конфигурационный формат

Ты придумал собственный конфиг, по духу похожий на RON, но в стиле TOML.

Синтаксис именно тот, который ты описал:

"" — строки.
'' — числа.
При этом в '' можно указывать систему счисления, например ''2 для двоичной и ''16 для шестнадцатеричной.
true / false — обычные bool без дополнительных обозначений.
null — отсутствие значения, тоже без дополнительных обозначений.
{} — массивы.
[] — таблицы/секции.
Например:
[id = '42']
Для даты/времени ты рассматриваешь отдельный тип через @...@, например:
@2020-02-20@
Enum обозначается через обратные кавычки:
``

Именно `` — enum, не что-то другое.

Вложенность таблиц
В [] указывается, к чему относятся последующие значения, как в TOML.
Например:
[config]
Если нужна вложенность, используется число после имени:
[settings]2
Это означает второй уровень вложенности.
Аналогично можно продолжать:
[something]3

и дальше сколько понадобится.

Компилятор и LLVM
Ты планируешь использовать LLVM.
Хочешь, чтобы компилятор не только компилировал, но и объяснял разработчику, что произошло.
Особенно интересует информация о том, какие оптимизации не удалось выполнить и почему.
Если LLVM уже умеет выдавать такие объяснения, ты хочешь использовать существующие механизмы, а не изобретать собственные.
В далёком будущем, если возможностей LLVM будет недостаточно, ты допускаешь собственный fork LLVM, чтобы получать более подробные объяснения.
Но начинать с форка ты не собираешься.
Тебе интересны существующие LLVM optimization remarks и подобные механизмы.
Объяснение машинного кода

Ты хочешь сделать несколько уровней соответствия:

твой код
   ↕
LLVM IR
   ↕
ASM
Пользователь должен иметь возможность понять, во что превратился его код.
LLVM IR здесь удобен как промежуточный слой.
Из IR уже можно смотреть, как LLVM получил ASM.
Желательно иметь соответствие между участком исходного кода и соответствующим IR/ASM.
Не обязательно обещать точное соответствие «одна строка → одна инструкция», потому что оптимизатор может объединять, разделять или полностью удалять код.
Идея — чтобы человек мог посмотреть только интересующий его участок, а не разбирать весь ассемблер.
Для ASM ты хотел бы иметь понятное текстовое объяснение инструкций, чтобы человек хотя бы в общих чертах понимал, что происходит.
Если конкретная инструкция непонятна, можно отдельно разобраться именно с ней.
Это должно сделать ASM последним уровнем проверки, а не обязательным первым инструментом.
Профилирование

Ты назвал это профилировщиком.

Но задумка шире обычного профилировщика:

профилировщик показывает, где реально тратится время;
компилятор/LLVM показывают, почему конкретный код не удалось оптимизировать;
пользователь может увидеть, что именно компилятор сделал или не сделал, не лезя постоянно в ASM;
получится своего рода встроенный инструмент объяснения производительности.

Общая идея всего языка у тебя при этом довольно единая: простота Go + нативность и отсутствие GC + безопасность памяти уровня Rust + явность Zig + максимально объяснимый компилятор, причём без необходимости заставлять каждого пользователя изучать всю сложность Rust ради обычной программы.
