# Идеи на будущее

## Скорость итератора без итераторов

Итератор как сущность языка не нужен: он требует значений с состоянием, которые в языке запрещены (`sub` не является значением, ссылки не прячутся в замыкания). Но его скорость нужна: обход через «обычный цикл» не должен проигрывать итератору, как это бывает в других языках.

## Принцип

> Скорость итератора — свойство компилятора, а не сущность языка.

Почему итераторы в Rust вообще выигрывают у «обычных циклов» — три вещи, которые компилятор делает с кодом итератора после инлайнинга: убирает проверки границ (у курсора честный диапазон, выход исключён по конструкции), убирает косвенность (next() за индексом ++), сводит запись-чтение-запись к прямому потоку без промежуточных аллокаций. Адаптеры map/filter — способ *выразить* всё это так, чтобы компилятор увидел цепочку разом. `while` проигрывает итератору ровно по этим пунктам: неизвестно, что `n` не изменится, что `i` не переполнится, что `a[i]` граница не нарушится.

## Правила понижения

1. `for item in list` понижается в IR как единый паттерн «курсор с зафиксированными base+len», а не разворачивается в `while`: выход за границы через курсор невозможен по конструкции — проверка не нужна, а не дешёвая.
2. То же правило понижения применяется к `while`-версии того же кода, если компилятор доказал заморозку/неизменяемость (см. правило индекс→указатель ниже). Быстрых и медленных способов обойти контейнер не существует — есть один опущенный паттерн и синтаксис, в котором человек его пишет.
3. Частые паттерны — встроенные формы `for`, понижаемые в тот же IR без промежуточных списков:

```text
for x in list.map(mul2) where x > 0 { ... }   // fusion: без промежуточного списка
for pair in zip(a, b) { ... }                 // два курса по одной итерации
for w in list.windows(3) { ... }              // скользящее окно = курсор с offset
```

Сахар, не сущности: у форм нет значений, нет состояния, их нельзя хранить и передавать. Раскрытие видно как у `!`-форм (см. 02-syntax.md).

4. Проверка на мутацию контейнера в теле — существующие правила убийства ссылок: контейнер мутанул — len/index пере-читывается, цикл честно перепроверяет. Программист не платит за случай, который не случился.

## Смысл

"Если можно быстрее — значит быстрее" догматически-простым способом: пользователь не выбирает между «простым» и «быстрым» циклом, потому что медленной формы в языке нет — она растворяется при понижении. Единственное, что может её вернуть, — мутация контейнера посреди обхода, и это честная цена, о которой язык ясно говорит правилом «change убивает link».

## Индексы как главный механизм доступа к куче

Идея: доступ к куче строится на индексах, а не на указателях. Индекс — значение: он проще указателя, его нельзя обменять на чужую память, его легко хранить, сравнивать, передавать. Проверка безопасности (границы, существование слота, принадлежность контейнеру) выполняется по индексу. А дальше — главный шаг:

> там, где компилятор доказал безопасность доступа, индекс превращается в прямой указатель.

Проверено один раз → дальше работа идёт как в C/Rust, с нулевой рантайм-ценой. Не везде, а везде, где доказательство дёшево — а их большинство.

### Почему потолок оптимизаций выше, чем у сырых указателей

Главная нерешаемая дорогая проблема оптимизатора в C и Rust — алиасинг: «а два указателя не смотрят ли в одну память?». Из-за неё нельзя вынести чтение из цикла, переупорядочить записи, свести копии к memcpy. C решает `restrict` (обещание), Rust — borrow checking'ом (сложный синтаксический анализ с lifetime'ами).

Индекс — это значение, доступ всегда идёт через явный канал «контейнер + индекс». В области, где безопасность доказана, компилятор автоматически получает:

- элементы не мутируются под ногами;
- реаллокации нет;
- границы проверены;
- алиасинга нет конструктивно.

Ни обещаний, ни отдельного анализа — это следствие правил языка, а не отдельная фича.

### Что даёт безопасность без lifetime'ов

Индекс сам по себе бессмыслен — он привязан к контейнеру-источнику. Эта привязка закрывается метками типов: `i32:id` (08-types.md).

```text
let user_i: i32:users = ...
fn get(i32:users idx) -> User { ... }
```

Метка привязывает индекс к контейнеру и проверяется на границах; в рантайме стирается — нулевая цена. Это половина времен жизни Rust, и для индексов её достаточно:

- метка = «какой контейнер» (как чей-то `[T]` адаптируется к индексу);
- жизнь самого контейнера контролирует существующий анализ.

Итак: метка типа = «какой контейнер», анализ жизни = «контейнер жив». Lifetime'ы не потребовались.

Правило кэширования указателя — не отдельная фича, а следствие существующих правил:

> Индекс, проверенный хотя бы раз в области, где контейнер заморожен (`link*`) или доказуемо неизменяем, эквивалентен прямому указателю и может кэшироваться компилятором. Любая мутация контейнера убивает и заморозку, и кэшированные указатели — как обычное убийство ссылок.

Это нельзя написать неправильно: `link*` замораживает данные, значит слот не исчезает и контракт обозначен. Оптимизатор доказательство получает из семантики языка, бесплатно.

### Где выжимать в первую очередь

Правило: выжимать максимум, но если сильно усложняется — забить. Язык остаётся простым; решение компилятора — там, где доказательство дёшево, обычный путь с проверкой — там, где дорого.

1. **Тело цикла по контейнеру.** Граница проверяется один раз (len зафиксирован в начале итерации), дальше кэш-указатель на базу или автопоследовательный доступ — прямое автопоследовательное векторизование внутри цикла (в side, миллионные операции).
2. **Замороженные данные (`link*`), читаемые в нескольких местах.** Все читатели получают прямые указатели без повторных проверок (связка с параллелизмом, 06-parallelism.md).
3. **Арены / самореференсные структуры** (деревья, графы). Индексы вместо рекурсивных типов — уже решение об этом. Разыменование узла цепочкой `node.children[j]` — три hops по памяти; попадание в cache-line — это критичное место выигрыша.

### Где забить (первая очередь «усложняется»)

- кэширование указателей через границы функций — всё, что требует межпроцедурного доказательства;
- хитрые паттерны удаления (если что-то и брать — то одним правилом поколений, а не выводом);
- «умная» статика границ для циклов с неизвестным len — рантайм-проверка, и хватит.

### Открытые вопросы

- Индексы при `box`-move контейнера: память не перемещается, меняется имя — индекс значим в «контейнер как данные», а не в «имя переменной»: поменять нужно формально зафиксировать.
- Удаление из нестабильных контейнеров: вариант — генерационные индексы (индекс + поколение в одном 64-битном значении), слот не переиспользуется сразу; концепт расширяемого `i32:id`.
- Индексы — не на всё: данные-значения (стек, поля структур) статически проверяемые и так — индексы для них не форсировать. Индексы заменяют именно тот класс, где раньше были указатели и запреты: цепочки ссылок, спрятанные в контейнерах, — то, что было нельзя сделать ссылкой, делается проверяемым индексом.

## Явный размер при создании вектора — не в v1

Когда создаётся контейнер, размер аллокации обязателен к написанию — в объектах, не в байтах:

```text
let v = vec [T; 64]        // знаешь размер: 64 объекта, компилятор сам умножит на размер типа
let v = vec [T; none]      // размер неизвестен: пустой вектор, аллоцируется постепенно
```

Правила:

- размер обязателен всегда — либо число, либо `none`; написать создание вектора без указания размера нельзя, это ошибка компиляции;
- размер пишется в объектах — перевод в байты делает компилятор, не программист;
- механика вектора не меняется: `none` — это текущее поведение (пустой + постепенная аллокация), явное число — заявка на объём, а не контракт;
- если реальных объектов окажется больше, чем заявлено, — вектор дорастает, как обычно, это не ошибка;
- два режима записаны в одном месте: знаешь размер — платишь одной точной аллокацией и видишь её в коде; не знаешь — честно получаешь постепенный рост.

Смысл: создание вектора — это момент рождения аллокации, и написание размера подтверждает, что программист об этом знает. Перерасход виден глазами в коде — не нужен бенч или профайлер, чтобы понять, что кто-то зарезервировал в десять раз больше, чем использует.

## Чертежи — не в v1

Чертёж — функция, в которой не указаны конкретные типы: вместо них оставлены места. Отдельного синтаксиса нет: это обычная функция без конкретных типов.

Когда места заполнены, получается шаблон — готовая функция с конкретными типами.

В v1 чертежи не входят: C-уровня достаточно без них.

## JIT-интерпретатор (встроенный в компилятор)

- Один язык, два способа запуска: AOT-компилятор и JIT-интерпретатор. Бэкенд один — Cranelift.
- Фронтенд отдаёт данные в JIT по готовности (по вычислениям и действиям), Cranelift компилирует на лету — REPL-режим, быстрое итерирование.
- Автоматическая память делает это естественным: никакого GC, компиляторные `free` работают и в JIT.
- Ценность: язык сам для себя скриптовый — написал, проверил, потом скомпилировал в быстрый бинарник.

## Comptime через JIT

JIT-бэкенд работает и как comptime-движок: выполнение кода на этапе компиляции (константы, генерация кода, компиляционные проверки).

Zig делает comptime интерпретацией — у нас JIT, быстрее.

Один бэкенд, три применения: AOT, JIT-интерпретация, comptime.
