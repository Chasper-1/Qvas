# Проверка ссылок

## Что проверяет компилятор

Компилятор отслеживает все ссылки (`link`, `link&` и `link*`) и проверяет четыре правила:

1. Ссылка не переживает объект/слот, на который указывает (точка последнего использования, конец области видимости) — compile-time.
2. State-bound ссылка (`link`) не используется после мутации пути, который она читает — compile-time.
3. Пока жива `link*`, мутация объекта/пути запрещена — compile-time.
4. Слот, на который смотрит `link&`, существует в момент использования — runtime-проверка, если смерть слота не доказуема статически.

Первые три проверки выполняются на этапе компиляции, на всех возможных путях исполнения. Четвёртая — это runtime-assert: компилятор не анализирует содержимое слота, он проверяет только, что путь валиден. Провал — panic, а не UB.

## Ссылка не убегает

Функция, принимающая ссылку, читает данные напрямую. Передача ссылки в другую функцию с `link`-параметром — не цепочка: передаётся то же окно в данные, а не ссылка на ссылку. Запрещён именно побег: вернуть ссылку, сохранить её в структуру/список/замыкание или использовать дольше жизни данных. Если данные нужны глубже или дольше — через `box` или индекс/арену.

## Условия и ветвления

Ветвления не являются принципиальной проблемой для проверки.

```text
if condition {
    use(x)
} else {
    discard(x)
}
```

Компилятор знает оба возможных пути и строит CFG:

```text
       condition
        /      \
      true    false
       |        |
     use(x)  discard(x)
        \      /
          end
```

Задача проверки — убедиться, что на всех возможных путях ссылки не переживают пути/слоты, которые они читают.

## Циклы

Циклы могут иметь неизвестное количество итераций:

```text
while condition {
    use(x)
}
```

Это не означает, что проверка невозможна. Компилятор использует стандартный data-flow/fixpoint-анализ.

## Runtime и compile-time

Компилятору не нужно заранее знать, какая именно ветка выполнится. Ему нужно знать, какие ветки вообще существуют и какие действия возможны на каждой из них.

Runtime выбирает конкретный путь. Compile-time анализирует множество возможных путей. Отдельно от выбора пути, `link&` проверяет существование слота в момент использования; эта проверка не зависит от того, какая ветка выполнилась.

## Внешние операции

Если данные покидают обычный контекст программы, это должно происходить через явную операцию:

- функция;
- структура;
- файл;
- API;
- устройство;
- системный вызов;
- другая внешняя граница;
- явное отбрасывание.

Для таких операций компилятору нужен контракт. Внешний код не обязан быть полностью проанализирован компилятором, но граница между ним и языком должна быть описана явно.

## Стоимость проверки

Проверка ссылок — это стандартный data-flow анализ для жизни, state-bound и заморозки; он выполняется на этапе компиляции. Существование слота для `link&` проверяется в рантайме, потому что зависит от данных; содержимое слота не анализируется. Слоты и ссылки явные, поэтому сам анализ проще вывода времени жизни.

Предпочтение отдаётся:

> больше работы во время компиляции → меньше ошибок во время выполнения.

## Формат ошибки

Мёртвая ссылка объясняется так: «вот эта ссылка, которую ты вот тут используешь, вот тут её вот так убили — то есть при использовании её уже не существует».

Формат compile-time ошибки:

> место использования ссылки → место и способ убийства (`mut`, move, смерть слота) → вывод.

Формат runtime panic для `link&`:

> место использования ссылки → слот исчез (удаление из контейнера, выход индекса за границы) → panic.
