# Проверка ссылок

## Что проверяет компилятор

Компилятор отслеживает все ссылки (`link`, `link&` и `link*`) и проверяет три правила:

1. Ссылка не переживает объект, на который указывает (точка последнего использования, конец области видимости).
2. State-bound ссылка не используется после мутации объекта.
3. Пока жива `link*`, мутация объекта запрещена.

Все три проверки — на этапе компиляции, на всех возможных путях исполнения.

## Ссылка не пробрасывается

Функция, принимающая ссылку, — конечный читатель. Она читает данные напрямую и не передаёт ссылку в другую функцию, принимающую ссылку: это создаёт цепочку через вызов. Данные передаются глубже через `box`.

## Условия и ветвления

Ветвления не являются принципиальной проблемой для проверки.

```text
if condition {
    use(x)
} else {
    discard(x)
}
```

Компилятор знает оба возможных пути и строит CFG:

```text
       condition
        /      \
      true    false
       |        |
     use(x)  discard(x)
        \      /
          end
```

Задача проверки — убедиться, что на всех возможных путях ссылки не переживают объекты.

## Циклы

Циклы могут иметь неизвестное количество итераций:

```text
while condition {
    use(x)
}
```

Это не означает, что проверка невозможна. Компилятор использует стандартный data-flow/fixpoint-анализ.

## Runtime и compile-time

Компилятору не нужно заранее знать, какая именно ветка выполнится. Ему нужно знать, какие ветки вообще существуют и какие действия возможны на каждой из них.

Runtime выбирает конкретный путь. Compile-time анализирует множество возможных путей.

## Внешние операции

Если данные покидают обычный контекст программы, это должно происходить через явную операцию:

- функция;
- структура;
- файл;
- API;
- устройство;
- системный вызов;
- другая внешняя граница;
- явное отбрасывание.

Для таких операций компилятору нужен контракт. Внешний код не обязан быть полностью проанализирован компилятором, но граница между ним и языком должна быть описана явно.

## Стоимость проверки

Проверка ссылок — это стандартный data-flow анализ, который выполняется на этапе компиляции. Он проще, чем вывод времени жизни: слоты и ссылки явные, ничего не нужно угадывать.

Предпочтение отдаётся:

> больше работы во время компиляции → меньше ошибок во время выполнения.

## Формат ошибки

Мёртвая ссылка объясняется так: «вот эта ссылка, которую ты вот тут передаёшь, вот тут её вот так убили — то есть при передаче её уже не существует».

Формат:

> место использования ссылки → место и способ убийства (`mut`, move, смерть слота) → вывод.
