# Параллелизм

## Механизм решён

Механизм (в дополнение к концепции графа) решён. Решение — взять существующие, проверенные планировщики и сделать их частью семантики языка: язык отвечает за корректность (кто от кого зависит), планировщик — за исполнение (как разложить по ядрам). Каждый делает своё.

## Граф зависимостей

Синтаксис: `parallel { ... }` — блок, в котором пишешь, что делать параллельно. Компилятор строит граф зависимостей и планирует сам.

```text
parallel {
    let x = compute_x()
    let files = load_files()
    let result = process(x, files)
}
```

Граф:

```text
compute_x ── x ──→ process
load_files ──────→ process
```

`compute_x` и `load_files` независимы — выполняются параллельно. `process` начинается только после получения необходимых результатов.

Построение графа — из порядка написания и зависимостей по данным: чтение того, что вычислила предыдущая нода, — ребро. Правила языка (`mut`, `box`, `link`) уже дают все рёбра:

- **`mut` внутри блока** — мутация = зависимость: если две ноды пишут в одну переменную, они сериализуются порядком написания. Независимые пишущие задачи — каждая в свою переменную.
- **Граница блока** — значения, созданные внутри, живут после блока; join'ы происходят автоматически по зависимостям. Отдельного `await`/`join` нет: ручная синхронизация возвращать не нужно.
- **Порядок написания по умолчанию** — приоритет: если нода зависит от следующей как-то, пишется сверху вниз; по большей части в блок пишутся независимые части.

## fn → rayon, sub → tokio

Маршрутизация нод графа по исполнителям — самая простая часть, потому что она уже видна на сущности:

- **`fn` — вычисление** (чистое: не вызывает `sub`, отдаёт ответ) — нода, которая в основном *считает*. Её место — **rayon**: work-stealing, разбиение по ядрам, воркеры.
- **`sub` — действие** (работа с миром: файлы, сеть, ввод-вывод) — нода, которая в основном *ждёт*. Её место — **tokio**: асинхронное исполнение, ожидание дешёвое.

Блок при этом никак не меняется: он всегда один и тот же — граф. Выбор «async или threads» — это не свойство кода, а маршрут ноды, и маршрут определяется тем, что написано в ноде: `sub` → tokio, `fn` → rayon. Смешанные графы разлетаются по двум исполнителям, а стык (вычислить после загрузки) — это просто ребро между ними.

Условия, на которых это безопасно, уже есть в модели языка:

- `fn` не вызывает `sub` (07-functions.md) — задачи графа чисты → порядок исполнения не влияет на результат → недетерминизм планировщика безопасен;
- `link*` заморозка — несколько задач читают одни данные без конфликтов, и это доказано компилятором, а не «надеемся на Sync»;
- `box`-передача — данные уходят задаче по move, источник умер: гонки за владение не существует по построению.

Следствие: асинхронность не меняет синтаксис исходника (нет async-заражения, нет цветных функций) — как у Go по исходнику, но с настоящим планировщиком, который видит весь граф.

## Общие данные и ссылки

Общие данные в параллельном блоке читаются через ссылки. `link*` замораживает данные на время параллельного чтения — никто не сможет их изменить.

```text
let data = load_data()
link* view = data

parallel {
    process_a(view)
    process_b(view)
}
```

`process_a` и `process_b` читают `view` напрямую. Передача `view` в них — не цепочка, а использование того же окна в данные; ссылку нельзя вернуть или сохранить, но вызвать с ней другое читающее вычисление или действие можно.

## Односторонние зависимости

Зависимость должна существовать только там, где она действительно нужна.

Если результат `A` нужен `B`, то достаточно:

```text
A
↓
B
```

Это не означает, что `B → A`. Независимые части программы не должны искусственно блокировать друг друга.

## Что описывает программист и что решается само

> программист описывает семантические зависимости, а не вручную расставляет каждую точку синхронизации для независимых операций.

Слои:

1. **Граф** — построение из порядка написания и зависимостей по данным (правила `mut`/`box`/`link` — сами рёбра).
2. **Маршрут нод** — по сущности: `sub` с IO ждёт → tokio, `fn` считает → rayon.
3. **Исполнение** — планировщик уже существует и проверен: rayon для считающих, tokio для ожидающих.

Низкоуровневые примитивы вроде mutex/atomic/channel при необходимости всё равно могут существовать.

## Параллелизм не равен безопасности памяти

Параллельное выполнение рассматривается как отдельный уровень.

Программа может быть:

- memory-safe, но логически неправильной;
- корректной по зависимостям;
- некорректной из-за неправильной организации параллельных операций.

Безопасность памяти и корректность параллельной логики не обязательно должны быть одной и той же системой правил.
