# Концепция языка

## 1. Введение

Язык задуман как низкоуровневый компилируемый язык без GC: простой примерно как Go, безопасный по памяти не хуже Rust, явный как Zig.

Основные цели:

* близкая к нативной производительность;
* предсказуемое поведение;
* отсутствие необходимости в тяжёлом runtime/GC;
* автоматическое управление памятью с проверкой ссылок на этапе компиляции;
* максимально простая модель изменения состояния;
* явность важных действий в исходном коде;
* безопасность памяти без необходимости воспроизводить модель Rust один в один.

Компилятор проверяет программу на этапе компиляции и генерирует обычный низкоуровневый код.

Ключевая формула проекта:

> **Максимум анализа во время компиляции, минимум обязательной работы во время выполнения.**

А модель изменения состояния:

> **Не «я разрешаю изменять это», а «я изменяю это прямо сейчас».**

---

## 2. Философия

Вся концепция сводится к следующим принципам:

### 1. Неизменяемость по умолчанию

Данные не меняются без явного действия.

### 2. `mut` обозначает действие

`mut` — это не постоянное разрешение, а конкретный переход состояния.

### 3. Ссылки по умолчанию привязаны к состоянию

```text
link b = a
```

создаёт контракт с текущим состоянием.

### 4. Изменение состояния разрывает старые state-bound контракты

После:

```text
mut a = ...
```

старые обычные ссылки на предыдущее состояние становятся недействительными.

### 5. Долгоживущая ссылка должна быть явной

```text
link& b = a
```

выражает привязку к самому объекту/памяти.

### 6. Нет состояния по умолчанию: чтение или использование

Каждое взаимодействие с данными — либо чтение, либо использование. Что именно — определяет контракт операции, куда переданы данные.

Читающие операции (условия, сравнения, длина) принимают ссылки. Потребление и копирование данных требуют databox — компилятор решает копия или move по числу использований.

Чтение — не потребление: читать можно сколько угодно раз.

### 7. Память автоматическая, компилятор проверяет ссылки

Компилятор управляет памятью автоматически. Компилятор проверяет, что ссылки не переживают объект, на который указывают.

### 8. Независимые действия могут выполняться параллельно

Зависимости образуют граф, который может использоваться для автоматического планирования.

### 9. Язык должен быть явным

Компилятор анализирует семантику, выраженную в программе. Он не должен угадывать намерения программиста там, где это не требуется.

### 10. Убирать лишнее, а не резать функционал

Язык не ограничивает возможности — он убирает лишнее. Всё, что реально нужно, остаётся: читать, копировать, перемещать, мутировать, передавать. Убираются только способы сделать это неправильно или избыточно: цепочки ссылок, ссылки, спрятанные в контейнерах, мутация через ссылку.

Это не резание функционала, а очистка: функционал тот же, а способов его испортить — ноль.

## 3. Состояния и мутация

### 3.1. Неизменяемость по умолчанию

Все значения и состояния по умолчанию считаются неизменяемыми.

Изменение существующего состояния требует явного `mut`.

```text
let x = 10
mut x = 15
mut x += 5
```

Концептуально это:

```text
x₀ = 10
  ↓ mut
x₁ = 15
  ↓ mut
x₂ = 20
```

### 3.2. `mut` — это действие, а не разрешение

`mut` не является постоянным свойством переменной.

Это не аналог:

```text
mutable x
```

и не разрешение «эту переменную теперь можно менять».

Смысл `mut`:

> «я прямо сейчас выполняю изменение состояния».

После изменения новое состояние снова считается неизменяемым.

Основной принцип:

> Не объявлять разрешение на изменение, а явно обозначать само изменение.

### 3.3. Состояния данных

Изменение объекта/значения рассматривается как переход между состояниями.

```text
let x = 10

mut x = 20
```

означает переход:

```text
state₀ → state₁
```

где:

```text
state₀: x = 10
state₁: x = 20
```

### 3.4. Мутация через методы

Мутация через вызовы функций/методов выражается тем же маркером:

```text
mut vec.push(x)
```

Сигнатура метода объявляет, что именно он мутирует (например, receiver). `mut` на вызове — маркер события изменения. Компилятор проверяет, что маркер соответствует сигнатуре.

Забытый `mut` на мутирующем вызове — ошибка компиляции.

## 4. Модель данных

### 4.1. Ключевые слова

| Ключевое слово | Значение |
|---|---|
| `let` | создать (переменную, enum) |
| `fn` | создать функцию |
| `link` | создать ссылку (чтение, умирает при `mut`) или подключить файл (`link file = "file.lang"`) |
| `link&` | долгоживущая ссылка (переживает `mut`) |
| `link*` | долгоживущая ссылка с заморозкой (данные нельзя изменить, пока ссылка жива) |
| `mut` | изменить |
| `databox` | использовать данные (компилятор решает копия/move) |
| `const` | константа (значение известно на этапе компиляции) |
| `use` | импорт модуля (std, пакеты) |

### 4.2. Механизмы работы с данными

| Механизм | Значение | Что происходит |
|---|---|---|
| `let b = a` | копия | создать независимое значение, `a` жива |
| `link b = a` | ссылка | чтение, `a` жива, умирает при `mut a` |
| `link& b = a` | ссылка на слот | чтение, привязана к памяти, переживает `mut a` |
| `link* b = a` | ссылка с заморозкой | чтение, привязана к памяти, `mut a` запрещён, пока ссылка жива |
| `databox(expr)` | реальные данные | компилятор выбирает копия или move |

Контракт операции определяет, что принимает операция: ссылку (чтение) или databox (использование).

Все операции проверяются компилятором. Использование мёртвой ссылки любого типа — ошибка компиляции.

`link` также подключает файлы: `link file = "file.lang"` — работаешь как с библиотекой, `file.sum()`. Файловая ссылка долгоживущая: `mut` её не убивает (файл не мутируется в модели языка). Ссылка на ссылку: `file::match.sum()` — `::` переход в ссылку внутри подключённого файла, `.` вызов функции. Цепочки разрешены, циклы — ошибка компиляции.

### 4.3. Нет состояния по умолчанию

Каждое взаимодействие с данными — либо чтение, либо использование. Нет «по умолчанию».

```text
let b = a
```

создаёт копию. `b` — независимое значение, `a` жива.

```text
link b = a
```

создаёт ссылку. `b` читает данные, `a` жива.

```text
let sum = databox(a + b)
```

использует реальные данные. Компилятор выбирает копия или move по числу использований:

* 1 использование → move (или копия, если лучше);
* 2+ использования → копия неизбежна.

```text
let result = add(a, b)              # чтение — ссылки, без databox
let result = add(databox(a), databox(b))   # использование — databox
```

### 4.3.1. Чтение — это не потребление

Чтение реализуется через ссылку (`link` или `link&`), ничего не изменяет и ничего не потребляет. Читать можно сколько угодно раз.

Потребление — это передача данных через databox. Компилятор решает: копия или move, в зависимости от числа использований.

Чтение — это только посмотреть. Взять — это databox.

### 4.4. `link b = a` — ссылка на текущее состояние

```text
let a = 20
link b = a
```

означает:

```text
a ─┐
b ─┘──→ [20]
```

Оба имени связаны с одним текущим состоянием данных.

Связь `link b = a` является контрактом с конкретным состоянием:

> `b` имеет право обращаться к текущему состоянию `a`.

### 4.5. Мутация разрывает state-bound контракт

Если затем происходит:

```text
mut a = 30
```

то создаётся новое состояние `a`.

Старый контракт:

```text
link b = a₀
```

больше не существует. `b` не превращается в dangling reference — старая версия состояния просто перестаёт быть допустимой для дальнейшего использования через этот контракт.

Использование `b` после `mut a` — ошибка компиляции.

Чтобы снова получить `b`, необходимо явно написать:

```text
link b = a
```

После этого:

```text
b → a₁
```

### 4.6. `link& b = a` — явная долговременная ссылка

Отдельный синтаксис для ссылки, которая привязана не к конкретной версии состояния, а к самой памяти/слоту:

```text
let a = 20
link& b = a

mut a = 30
```

В этом случае `b` остаётся связанной с той же памятью и после изменения `a` видит новое значение.

Разница:

```text
link b = a
```

— ссылка на конкретное состояние.

```text
link& b = a
```

— явная привязка к самому слоту/памяти.

`link&` не делает ссылку бессмертной: когда слот умирает (например, переменная выходит из области видимости или объект освобождается), ссылка умирает вместе с ним. Использование `link&`-ссылки после смерти слота — ошибка компиляции.

Главная идея:

> Обычная ссылка короткоживущая и привязана к состоянию. Долгоживущая ссылка должна быть выражена отдельным синтаксисом.

### 4.6.1. `link* b = a` — ссылка с заморозкой

`link*` — самая сильная гарантия: пока ссылка жива, данные, на которые она указывает, нельзя изменить вообще. Ни через ссылку, ни через оригинал.

```text
let a = 20
link* b = a

mut a = 30    # ОШИБКА: a заморожена, пока жива link* b
```

Когда `link*` умирает (вместе со слотом, как `link&`), заморозка снимается.

Разница:

```text
link& b = a    # «я хочу видеть изменения слота» — mut a можно, b следует за изменениями
link* b = a    # «данные не изменятся, пока я смотрю» — mut a запрещён
```

Зачем нужен `link*`:
- параллельный доступ — несколько потоков читают, никто не мутирует;
- инварианты — данные не изменятся, пока обрабатываются;
- кэширование — значение гарантированно валидно.

Использование мёртвой `link*` — ошибка компиляции, как и любой другой ссылки.

Контроль привязан к потребителю, а не к данным: пока данных никто не читает — они свободны. Появился потребитель (`link*`) — данные заморожены. Ссылка умерла — контроль выключился.

### 4.7. Databox — перемещение или копия

```text
let a = big_object
let b = databox(a)
```

Компилятор решает: если `a` используется один раз — move, данные переезжают под `b`, `a` мертва. Если `a` используется 2+ раза — копия, `a` жива.

Никакого «владения» как отдельной концепции нет: компилятор решает копия или move, в зависимости от числа использований.

### 4.8. Копия и независимость

Копия создаётся автоматически, когда компилятор видит, что данные используются 2+ раза. Явное копирование больше не нужно — компилятор решает.

`b` и `a` больше никак не связаны: мутация `a` не влияет на `b`, и наоборот.

Копия — единственный способ получить независимое значение.

### 4.9. Логические ошибки — ответственность кода

Компилятор гарантирует безопасность памяти: мёртвая ссылка любого типа не может быть использована.

Компилятор не решает логические ошибки. Пример:

```text
let a = 10
link& b = a

mut a = new_object
```

С памятью всё в порядке: `b` жива, слот жив, `b` видит новое значение. Но если `b` ожидала данные старого объекта — это семантическая ошибка кода, а не языка. Язык не умеет и не должен решать логические проблемы программы.

### 4.10. Выбор механизма — заявка на намерение

Выбор механизма выражает намерение программиста:

* `let b = a` — «мне нужна независимая копия»;
* `link b = a` — «мне нужно прочитать данные»;
* `link& b = a` — «я хочу видеть изменения слота»;
* `databox(expr)` — «я использую реальные данные, компилятор решит копия или move».

Контракт операции определяет, что принимать: ссылку (чтение) или databox (использование). Если планируется замена объекта, компилятор поймает любое использование после неё.

### 4.10. Ссылки на элементы

Ссылка может быть создана непосредственно на нужный элемент:

```text
link b = a[0]
```

означает ссылку на соответствующий элемент текущего состояния.

Если `a` затем изменяется:

```text
mut a = ...
```

обычная связь с предыдущим состоянием `a[0]` прекращается. Даже если после изменения в `a[0]` случайно находится такое же значение, это уже новое состояние.

Инвалидация при мутации — целого объекта: любая мутация `a` убивает все state-bound ссылки, производные от `a`, включая ссылки на элементы.

Если необходимо сохранить привязку к самой памяти, используется долговременная форма ссылки.

### 4.11. Ссылка — это чтение

Через ссылку можно только читать. Изменить или мутировать через ссылку нельзя — это не её функция. Копия делается от переменной с данными: `let c = a`, а не через ссылку.

Чтение не потребляет: через ссылку можно читать сколько угодно раз. Потребление — это передача значения (move), а не чтение.

Мутация — это `mut` на самой переменной, где лежат данные. Ссылка на это не способна в принципе.

Ссылка безопасна по определению: через неё физически нельзя ничего сломать, потому что она только читает. И она умирает при мутации, потому что данные, на которые она смотрела, изменились, — а она читала старое состояние.

`link*` усиливает это до заморозки: пока ссылка жива, данные нельзя изменить даже через оригинал.

### 4.12. Ссылки прямые, без цепочек

Ссылка всегда указывает прямо на данные. Ссылку можно создать только от переменной, в которой лежат данные. От другой ссылки — нельзя.

```text
link b = a
link c = b    # запрещено: ссылка от ссылки
```

Хочешь ссылку на данные — пиши прямо на переменную с данными:

```text
link c = a    # правильно
```

Цепочки невозможны в принципе — не потому что компилятор их ловит, а потому что их нельзя написать. Ссылка всегда указывает прямо на данные, и это гарантировано самим языком.

### 4.13. Ссылки не прячутся

Ссылка короткоживущая: живёт там, где создана, и умирает там же. Ссылку не кладут в списки и не хранят в других местах — это не делается.

Если данные нужны кому-то надолго — их не прячут в ссылку, а передают через databox (move или копия). Данные либо у тебя, либо переданы другому, либо скопированы. Третьего не дано.

### 4.14. Move убивает ссылки

При перемещении (когда databox решает move) исходная переменная умирает — данные переехали под новое имя. Вместе с ней умирают все ссылки на неё: ссылаться на мёртвую переменную нельзя.

```text
let a = big_object
link b = a            # ссылка на a
let c = databox(a)    # a: 1 использование → move, a мертва
print(b)              # ошибка: b мертва вместе с a
```

Правило простое: исходная переменная умерла — ссылки на неё мертвы.

### 4.15. Модификаторы типов

`int:id` — модификатор, не отдельный тип данных. Создаётся значением:

```text
let user_id: int:id = 42
```

Теперь 42 — это `int:id`. 42 не перестаёт быть int — все int-операции работают. Но это `int:id`.

Функция запрашивает модифицированный тип:

```text
fn get_user(int:id user_id) -> User { ... }
```

Передать можно только `int:id`. Обычный int не подойдёт — модификатора нет.

Именованные алиасы не нужны: метка видна прямо на типе, ничего искать не надо.

Есть второй вариант — `int:=id`. Это не контракт типа, а указание источника данных: «данные даёт вот эта переменная — `id`».

```text
fn print(int:=data) { ... }
```

`int:=id` используется только там, где данные принимаются (параметры функций и т.п.): внутри данные доступны по имени `id`. Имя важно — это источник.

Разница:

* `int:id` — контракт типа: «передаются данные типа `int:id`». Кто даёт — не важно, важно, что за тип. Можно везде.
* `int:=id` — источник данных: «данные даёт переменная `id`». Имя важно. Только при приёме данных.

Зачем: не всегда можно заранее подготовить типы данных. `int:=id` позволяет написать, откуда придут данные конкретного типа — безопасно и без сложностей в логике. Один раз написал, что нужно тут, — и ошибок не будет.

Единицы измерения — это просто модификатор: `int:meters`. Никакой специальной арифметики единиц нет (метры², метры/секунды не вычисляются). Объявил `int:meters` — и передавай, куда нужно. Контракт — модификатор.

Диапазоны — не в типы. Проверка диапазона — тупое сравнение, легко пишется явно. Модификатор типа скрывал бы действие и делал его менее понятным, к тому же допускал бы выполнение действия разными способами. Если нужно — явная возможность писать о диапазоне (переменная, сигнатура функции), а не модификатор типа.

Принцип: в типы идёт только то, что нельзя проверить обычным кодом. `int:id` и `int:=id` — семантические свойства, обычным кодом не проверяются → обязательны. Диапазоны — проверяются обычным кодом (`if x > 100`) → не в типы.

## 5. Память

### 5.1. Автоматическое управление

Памятью управляет компилятор. Программист не пишет `alloc` и `free` — компилятор сам решает, где выделить (стек или куча, escape analysis) и когда освободить.

Освобождение — в точке последнего использования данных (как NLL в Rust). Анализ времён жизни, который проверяет ссылки, и так знает, когда данные мертвы: вставка `free` не требует отдельного прохода.

Автоматическое управление детерминированное: никакого GC, никакого подсчёта ссылок, никаких пауз. Это просто компиляторные `free` в известных точках.

### 5.2. Компилятор проверяет ссылки

Компилятор проверяет ссылки: ссылка не может пережить объект, на который указывает. Данные умирают в точке последнего использования (или в конце области видимости), и ссылка не может использоваться после этого.

```text
let a = ...
link b = a        # ссылка на значение
std.print(b)      # последнее использование данных
# здесь данные мертвы — компилятор освободил память
```

Ссылаться на то, чего нет, нельзя по определению. Это ошибка компиляции, а не runtime-проверка.

### 5.3. Почему автоматическое управление

Программист не должен думать о памяти, когда она и так работает детерминированно. Ручное выделение требует знать, где именно нужна память, а ошибка в этом месте — логическая, компилятор её не ловит.

Автоматическое управление + проверка ссылок дают:

* предсказуемое поведение — освобождение в точке последнего использования, без пауз и сборщика;
* простые проверки — анализ времён жизни и так нужен для проверки ссылок, вставка `free` бесплатна;
* безопасность памяти — компилятор сам решает, где выделить и когда освободить.

Цель языка — не дать стрелять себе в ногу при написании. Компилятор ловит очевидные ошибки на этапе компиляции и сам управляет памятью.

### 5.4. Перемещение и копия

Компилятор решает: если данные используются один раз — move, данные переезжают под новое имя, старое имя умирает. Если данные используются 2+ раза — копия, создаётся независимое значение.

Это передача, а не владение. Владение — это передача плюс много лишнего. Передача — это передача, не больше и не меньше: данные переехали, старое имя мертво. Вместе со старым именем умирают и ссылки на него.

Для больших объектов копия может быть дорогой; оптимизатор может превращать безопасные копии в перемещения, но решение принимает компилятор, а не программист.

## 6. Проверка ссылок

### 6.1. Что проверяет компилятор

Компилятор отслеживает все ссылки (`link`, `link&` и `link*`) и проверяет три правила:

1. Ссылка не переживает объект, на который указывает (точка последнего использования, конец области видимости).
2. State-bound ссылка не используется после мутации объекта.
3. Пока жива `link*`, мутация объекта запрещена.

Все три проверки — на этапе компиляции, на всех возможных путях исполнения.

Объяснение ошибки: «вот эта ссылка, которую ты вот тут передаёшь, вот тут её вот так убили — то есть при передаче её уже не существует». Формат: место использования ссылки → место и способ убийства (`mut`, move, смерть слота) → вывод.

### 6.2. Условия и ветвления

Ветвления не являются принципиальной проблемой для проверки.

```text
if condition {
    use(x)
} else {
    discard(x)
}
```

Компилятор знает оба возможных пути и строит CFG:

```text
       condition
        /      \
      true    false
       |        |
     use(x)  discard(x)
        \      /
          end
```

Задача проверки — убедиться, что на всех возможных путях ссылки не переживают объекты.

### 6.3. Циклы

Циклы могут иметь неизвестное количество итераций:

```text
while condition {
    use(x)
}
```

Это не означает, что проверка невозможна. Компилятор использует стандартный data-flow/fixpoint-анализ.

### 6.4. Runtime и compile-time

Компилятору не нужно заранее знать, какая именно ветка выполнится. Ему нужно знать, какие ветки вообще существуют и какие действия возможны на каждой из них.

Runtime выбирает конкретный путь. Compile-time анализирует множество возможных путей.

### 6.5. Внешние операции

Если данные покидают обычный контекст программы, это должно происходить через явную операцию:

* функция;
* структура;
* файл;
* API;
* устройство;
* системный вызов;
* другая внешняя граница;
* явное отбрасывание.

Для таких операций компилятору нужен контракт. Внешний код не обязан быть полностью проанализирован компилятором, но граница между ним и языком должна быть описана явно.

### 6.6. Стоимость проверки

Проверка ссылок — это стандартный data-flow анализ, который выполняется на этапе компиляции. Он проще, чем вывод времени жизни: слоты и ссылки явные, ничего не нужно угадывать.

Предпочтение отдаётся:

> больше работы во время компиляции → меньше ошибок во время выполнения.

## 7. Параллелизм

### 7.1. Граф зависимостей

Синтаксис: `parallel { ... }` — блок, в котором пишешь, что делать параллельно. Компилятор строит граф зависимостей и планирует сам.

```text
parallel {
    let x = compute_x()
    let files = load_files()
    let result = process(x, files)
}
```

Граф:

```text
compute_x ── x ──→ process
load_files ──────→ process
```

`compute_x` и `load_files` независимы — выполняются параллельно. `process` начинается только после получения необходимых результатов.

### 7.2. Односторонние зависимости

Зависимость должна существовать только там, где она действительно нужна.

Если результат `A` нужен `B`, то достаточно:

```text
A
↓
B
```

Это не означает, что `B → A`. Независимые части программы не должны искусственно блокировать друг друга.

### 7.3. Автоматическое планирование

Компилятор может преобразовать зависимости в граф задач и затем выбрать способ их выполнения:

* последовательно;
* параллельно;
* на отдельных потоках;
* через worker pool;
* через другой лёгкий scheduler.

Главная идея:

> программист описывает семантические зависимости, а не вручную расставляет каждую точку синхронизации для независимых операций.

Низкоуровневые примитивы вроде mutex/atomic/channel при необходимости всё равно могут существовать.

### 7.4. Параллелизм не равен безопасности памяти

Параллельное выполнение рассматривается как отдельный уровень.

Программа может быть:

* memory-safe, но логически неправильной;
* корректной по зависимостям;
* некорректной из-за неправильной организации параллельных операций.

Безопасность памяти и корректность параллельной логики не обязательно должны быть одной и той же системой правил.

Общие данные в параллельном блоке читаются через ссылки. `link*` замораживает данные на время параллельного чтения — никто не сможет их изменить.

## 8. Обучение

Одна из главных целей — чтобы базовую модель языка можно было понять примерно за пять минут и сразу применять.

Модель сводится к нескольким правилам:

1. Данные неизменяемы по умолчанию.
2. `mut` — это событие изменения, а не разрешение.
3. Нет состояния по умолчанию: чтение или использование — определяет контракт операции.
4. `let b = a` — копия (создать независимое значение).
5. `link b = a` — ссылка (чтение). `link& b = a` — ссылка на слот (чтение, привязана к памяти). `link* b = a` — ссылка с заморозкой (чтение, данные нельзя изменить, пока ссылка жива).
6. `databox(expr)` — использование реальных данных. Компилятор решает: копия (2+ использования) или move (1 использование).
7. `const a = 10` — константа, значение известно на этапе компиляции.
8. Использование мёртвой ссылки — ошибка компиляции.
9. Ссылка — это чтение: через неё нельзя мутировать.
10. Ссылки прямые, без цепочек; ссылки не прячутся.
11. Move убивает ссылки: исходная переменная умерла — ссылки на неё мертвы.
12. Память автоматическая: компилятор сам выделяет и освобождает, проверяет ссылки.
13. Параллелизм: `parallel { ... }` — блок, компилятор строит граф зависимостей и планирует сам.

Возможны два варианта обучения:

* для новичков — с базовыми концепциями;
* для опытных — без повторного объяснения очевидных основ.

## 9. Зоны

### 9.1. Официальный синтаксис зон

Код делится на зоны через `---`:

```text
--- зона 1
код зоны 1

--- зона 2
код зоны 2
```

`---` — официальный синтаксис языка. Он не влияет на исполнение кода: зоны — это чисто структура, а не поведение.

Зоны плоские: ровно как написано в файле, никуда не вкладываются и не должны.

### 9.2. Описание зоны

После `---` на той же строке можно написать что угодно — название или описание зоны:

```text
--- чтение файла
код

--- обработка данных
код
```

Это не комментарий. Это часть официального синтаксиса: описание привязано к зоне и видно компилятору.

### 9.3. Зачем это нужно

Главная цель — отделить импорты от приёма/передачи и от кода, чтобы это было мега очевидно. Удобная штука, которая не влияет напрямую на компиляцию.

Сейчас компилятор ничего с зонами не делает — это просто удобство, не более. В будущем, возможно, компилятор сможет размечать зоны в своём AST на более мелкие структуры — отдельные или совместные — и взаимодействовать с ними. Но это будущие возможности, они сильно зависят от человека.
