## Что уже решено

### Ключевые слова

| Ключевое слово | Значение |
|---|---|
| `let` | создать (переменную, enum) |
| `fn` | создать функцию |
| `link` | создать ссылку (чтение, умирает при `mut`) или подключить файл (`link file = "file.lang"`) |
| `link&` | долгоживущая ссылка (переживает `mut`) |
| `link*` | долгоживущая ссылка с заморозкой (данные нельзя изменить, пока ссылка жива) |
| `mut` | изменить |
| `databox` | использовать данные (компилятор решает копия/move) |
| `const` | константа (значение известно на этапе компиляции) |
| `use` | импорт модуля (std, пакеты) |

### Модель данных и ссылок
- Нет состояния по умолчанию: каждое взаимодействие с данными — либо чтение, либо использование. Что именно — определяет контракт операции, куда переданы данные.
- Контракт операции: каждая операция заранее объявляет, читает она или потребляет. Без угадывания — гарантия написана. Список контрактов составляет автор языка.
- Читающие операции (условия, сравнения, длина, print, если так определён): принимают ссылки. Databox не нужен.
- Потребляющие операции (сложение, хранение в список, передача в потребляющую функцию): требуют реальные данные → databox.
- `let b = a` — копия (создать независимое значение). `a` жива.
- `link b = a` — ссылка (чтение). Нейтральная, `a` жива. Умирает при `mut a`.
- `link& b = a` — долгоживущая ссылка. Привязана к памяти, переживает `mut a`. Умирает со слотом.
- `link* b = a` — долгоживущая ссылка с заморозкой. Привязана к памяти, `mut a` запрещён, пока ссылка жива. Умирает со слотом.
- Databox: `databox(b + c)` — «использую реальные данные». Компилятор выбирает копия или move:
  - Данные используются 1 раз → move (или копия, если лучше).
  - Одни и те же данные используются 2+ раз → копия неизбежна.
- Ссылка читает данные. Передать ссылку в потребляющую операцию нельзя — потребляющая операция требует databox.
- Чтение — это не потребление: читать можно сколько угодно раз. Потребление — это передача данных.
- `const a = 10` — константа, значение известно на этапе компиляции. Инлайнится, вычисляется на этапе компиляции.
- Синтаксис `databox` — рабочий, можно сократить (dtbox, скобки) — мелочь.
- Ссылки прямые, без цепочек: ссылку можно создать только от переменной с данными, не от другой ссылки.
- Ссылки не прячутся: короткоживущие, живут там, где созданы, в списки не кладутся.
- Move убивает ссылки: исходная переменная умерла — ссылки на неё мертвы.
- Мутация убивает state-bound ссылки (`link`).
- Смерть слота убивает slot-bound ссылки (`link&`, `link*`).
- Использование мёртвой ссылки любого типа — ошибка компиляции.
- Инвалидация при мутации — целого объекта: любая мутация `a` убивает все ссылки, производные от `a`, включая ссылки на элементы.
- Ссылка может быть создана на элемент (`a[0]`).

### Мутация
- Неизменяемость по умолчанию.
- `mut` — это событие изменения, а не разрешение.
- Мутация через методы: `mut vec.push(x)`.
- Созданную переменную можно изменить: `mut a = c` — право есть, потому что создал.

### Память
- Память автоматическая: компилятор сам решает, где выделить (стек/куча, escape analysis) и когда освободить (точка последнего использования).
- Никакого GC и подсчёта ссылок — детерминированные компиляторные `free`.
- Компилятор проверяет ссылки: ссылка не может пережить объект.
- Use-after-free — ошибка компиляции, не runtime.
- Передача, а не владение: передача данных — не больше и не меньше.

### Философия
- Убирать лишнее, а не резать функционал.
- Логические ошибки — ответственность кода, не языка.
- Максимум анализа во время компиляции, минимум работы во время выполнения.
- Язык должен быть явным.

### Параллелизм
- Синтаксис: `parallel { ... }` — блок, в котором пишешь, что делать параллельно.
- Компилятор строит граф зависимостей и планирует сам: независимые действия — параллельно, зависимые — по порядку.
- Параллелизм не равен безопасности памяти: общие данные читаются через ссылки, `link*` замораживает данные на время параллельного чтения.

### Прочее
- Шаблоны = дженерики; шаблоны всегда раскрываются/инлайнятся.
- Enum в конфиге — одинарные обратные кавычки `` `...` ``.

### Типы
- Типы статические, 100%.

### Области видимости (концепция)
- Глобальная область — на весь файл.
- Локальная область — тело создаёт свою область видимости (например, функция). За пределами функции то, что написано внутри, не может быть использовано ни в каком виде. Где кончилась функция — там кончились возможности использования всего, что было написано ранее.
- Между файлами общее передаётся через функции: файл делает что нужно и передаёт результат в другой файл (`file.func()`). Общих глобалов на проект нет.

### Обработка ошибок
- Подход: ошибка — это фича, а не баг.
- Механизм по-Zig: встроенный, функция помечена «возвращает значение или ошибку», проброс одной командой, ловля одной командой.
- Содержимое по-Rust: ошибка — значение любого типа (имя, число, строка, структура с полями).
- Ленивый режим: компилятор сам генерирует номер ошибки из места (файл, строка, функция), номер ищешь в доках.
- Подробный режим: сам пишешь, что положить в ошибку.
- Лучше этого ошибки не сделать — только номерами.

### Конфиг
- Формат конфига уже определён (наработки в `my-lang.md`): строки `""`, числа `''`, массивы `{}`, таблицы `[]`, enum `` `...` ``.

### Функции
- Объявление: `fn name(params) -> type { ... }` — без `let`, `fn` сам создаёт функцию.
- Параметры с типами: `fn sum(a: int, b: int) -> int`.
- Контракт функции: параметры объявляют, читают они или потребляют. Видно в сигнатуре.
- Читающий параметр — `link` (ссылка). Потребляющий параметр — `databox` (компилятор решает копия или move по числу использований у вызывающего).
- Копия данных берётся от переменной с данными: `let c = a`, а не через ссылку. Ссылка читает.
- Возврат — это передача данных назад.
- Мутация данных в функции: данные пришли (потребление), поменялись через `mut`, вернулись (return = передача). Отдельный механизм не нужен.
- `mut` и move не смешиваются: `mut` меняет значение, move уносит данные. Либо одно, либо другое.

### Синтаксис
- Переменные: `let name = value`, явный тип `let name: type = value`.
- Функции: `fn name(params) -> type { ... }`, параметры с типами.
- Условия: `if cond { ... } else if ... { ... } else { ... }`, if-выражение.
- Switch: `switch x { 1 => ..., else => ... }`, выражение.
- Циклы: `for i in 0..10 { ... }`, `for item in list { ... }`, `while cond { ... }`, `break`/`continue`.

### Типы
- Типы статические, 100%.
- Базовые типы: все типы.

### Модификаторы типов
- `int:id` — модификатор, не отдельный тип. Создаётся: `let user_id: int:id = 42` — теперь 42 это `int:id`.
- 42 не перестаёт быть int — все int-операции работают. Но это `int:id`.
- Функция запрашивает модифицированный тип: `fn get_user(int:id user_id)`.
- Передать можно только `int:id`. Обычный int не подойдёт — модификатора нет.
- Именованные алиасы не нужны: метка видна прямо на типе, ничего искать не надо.
- `int:=id` — источник данных: «данные даёт переменная `id`». Только при приёме данных (параметры функций и т.п.). Имя важно.
- Разница: `int:id` — контракт типа (кто даёт не важно), `int:=id` — источник (имя важно).
- Единицы измерения — просто модификатор (`int:meters`), без арифметики единиц. Контракт — модификатор.
- Диапазоны — не в типы: проверка — тупое сравнение, пишется явно; модификатор скрывал бы действие. Если нужно — явная возможность писать о диапазоне (переменная, сигнатура функции).
- Принцип: в типы идёт только то, что нельзя проверить обычным кодом. `int:id`/`int:=id` — нельзя → обязательны. Диапазоны — можно (`if`) → не в типы.

### Компилятор
- Компилятор строится на Cranelift.
- Оптимизации — во фронтенде: явная модель даёт точный алиасинг, точные времена жизни, нет скрытого состояния → высокоуровневые оптимизации (инлайнинг, устранение копий, escape analysis) делает фронтенд.
- Cranelift — кодогенерация (регистры, планирование). Его проходы не отключаем — они бесплатны и дополняют.
- Главная инженерная работа: IR (SSA, с семантикой языка). AST → IR → оптимизации → Cranelift.
- Плоский AST (арена): один `Vec<Node>`, индексы вместо указателей — быстрее и проще. Как ECS в геймдеве.
- Полностью без дерева — только быстрый путь для простого кода; общий путь — арена (анализ ссылок/databox/параллелизм нуждаются в структуре).
- Inlining и move/copy (databox) — решает фронтенд по числу использований.
- Backend-friendly IR: изучить, какие паттерны узнаёт оптимизатор Cranelift, и давать ему ровно их.
- Синтаксис глобально не меняется; возможны микро-доработки для простоты разбора.

### Модули
- Модуль — файл.
- Импорт модуля: `use std` — вверху файла пишешь, что получаешь (как в Rust).
- Подключение файла: `link file = "file.lang"` — работаешь как с библиотекой.
- Вызов одинаковый: `std.print()`, `file.sum()` — имя + точка + функция.
- Ссылка на ссылку: `file::match.sum()` — `::` переход в ссылку внутри подключённого файла, `.` вызов функции.
- Цепочки разрешены, циклы (a ↔ b) — ошибка компиляции.
- Передача явная: в месте вызова видно, куда передаёшь.
- Две гарантии: видишь отдающую сторону и принимающую — ошибиться невозможно.
- Не определился, куда отдать — значит, не надо и передавать.

### Зоны
- `---` — официальный синтаксис, делит код на зоны.
- Зоны плоские, не вкладываются.
- На исполнение не влияет — чисто структура.
- Главная цель: отделить импорты от приёма/передачи и от кода, чтобы было мега очевидно.
- После `---` на той же строке можно написать описание зоны — это не комментарий, а часть синтаксиса.
- Компилятор пока ничего с зонами не делает — просто удобство. Будущие возможности: разметка зон в AST, взаимодействие с ними.

### Синтаксический сахар

**Брать (дёшево, ничего не скрывает):**
- Интерполяция строк.
- Диапазоны + `for..in`.
- `while` — цикл «пока условие истинно».
- if-выражение (явнее тернарника).
- Методы (`mut vec.push(x)`).
- Вывод типов, когда тип очевиден.
- `defer` — отложенное выполнение (закрытие ресурсов и т.п.).
- `try` — проброс ошибки одной командой.
- Слайсы (`a[1:3]`).
- Кортежи / несколько возвращаемых значений.
- Switch.
- Модификаторы типов (`int:id`).
- Сокращённая запись структур (`{имя, возраст}`).
- Неявный возврат последнего выражения.
- `break`/`continue`, `else if`.
- `+=` — составное присваивание: явное, ускоряет очевидное.
- Comptime — реализуемо: вычисление на этапе компиляции требует усилий, но делается со всеми гарантиями.

**Не брать (не обязательно):**
- Перегрузка операторов — скрывает, что под `+`; Go и Zig живут без неё.
- Исключения — ошибки это значения (решено); исключения — скрытый поток управления.
- Pattern matching (Rust-style) — сложно; switch покрывает 90% нужд.
- Null-операторы — в модели нет null.
- Аргументы по умолчанию / именованные — сложность разбора.
- Макросы — язык в языке; шаблоны покрывают главное. По ситуации: если не выйдет реализовать простым образом — пожертвовать.
- Интерфейсы/трейты — абстракция поверх абстракции. По ситуации: если не выйдет реализовать простым образом — пожертвовать.
- Async/await — параллелизм через граф зависимостей, другая модель.
- Корутины/генераторы — сложно, редко нужно.
- Рефлексия — сложно, против явности.
- GC/RAII — память автоматическая, без GC.
- Enum с данными (sum types) — сложно, простых enum'ов хватает. По ситуации: если не выйдет реализовать простым образом — пожертвовать.
- Цепочные сравнения, метки циклов — редко нужно.
- Принцип: не резать функционал. То, что не строим в v1, проектируем так, чтобы можно было добавить потом без поломки.

## Идеи на будущее

### JIT-интерпретатор (встроенный в компилятор)
- Один язык, два способа запуска: AOT-компилятор и JIT-интерпретатор. Бэкенд один — Cranelift.
- Фронтенд отдаёт данные в JIT по готовности (по функциям), Cranelift компилирует на лету — REPL-режим, быстрое итерирование.
- Автоматическая память делает это естественным: никакого GC, компиляторные `free` работают и в JIT.
- Ценность: язык сам для себя скриптовый — написал, проверил, потом скомпилировал в быстрый бинарник.

### Comptime через JIT
- JIT-бэкенд работает и как comptime-движок: выполнение кода на этапе компиляции (константы, генерация кода, компиляционные проверки).
- Zig делает comptime интерпретацией — у нас JIT, быстрее.
- Один бэкенд, три применения: AOT, JIT-интерпретация, comptime.
